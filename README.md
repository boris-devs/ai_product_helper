# AI Product Helper

Прототип сервиса, который по данным о контрольно-измерительном приборе (название, производитель, характеристики, описание) готовит черновик карточки товара для B2B-интернет-магазина.

Для каждого прибора сервис формирует:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- список ключевых характеристик: значения берутся только из входных данных, отсутствующие помечены «данных нет»;
- 3–5 поисковых запросов, под которые стоит оптимизировать страницу;
- коммерческий блок для менеджера: кому подходит прибор и какие задачи решает;
- список полей, которые нужно уточнить, и предупреждения автоматической проверки.

Результат отдаётся в JSON и Markdown. Данные можно ввести в веб-форме или отправить JSON в API. Каждая генерация сохраняется в PostgreSQL.

## Быстрый старт (Docker)

Нужны только Docker и ключ OpenRouter ([openrouter.ai/keys](https://openrouter.ai/keys)).

1. Создайте файл настроек:

```bash
cp .env.example .env
```

2. Откройте `.env` и впишите:
   - `OPENROUTER_API_KEY` — ваш ключ;
   - `OPENROUTER_MODEL` — идентификатор модели с [openrouter.ai/models](https://openrouter.ai/models), например `openai/gpt-4o-mini` или `google/gemini-2.5-flash`.

   Файл `.env` добавлен в `.gitignore`, ключ в репозиторий не попадёт.

3. Запустите:

```bash
docker compose up --build
```

При старте контейнер применяет миграции (`alembic upgrade head`) и запускает сервер.

- Веб-форма: http://localhost:8000
- Документация API (Swagger): http://localhost:8000/docs

После изменения `.env` достаточно перезапустить контейнеры, пересборка не нужна:

```bash
docker compose up -d
```

### Выбор модели

Нужна обычная instruct-модель, не reasoning-модель и не совсем маленькая: слабые модели хуже держат JSON и чаще нарушают требования к длине и достоверности. Бесплатные модели (`:free`) на OpenRouter имеют жёсткие лимиты и часто отвечают 429.

### Примеры результатов

Когда сервис запущен и ключ задан:

```bash
docker compose exec app python scripts/generate_examples.py
```

Скрипт отправит каждый файл из `examples/input/` в API и сохранит ответы в `examples/output/` (`*.json` и `*.md`).

| Файл | Что показывает |
|---|---|
| `01_manometer_dm02.json` | манометр из задания с дополненным описанием |
| `02_pressure_transmitter.json` | демо-датчик с питанием и выходным сигналом; пустой «класс точности»; IP65 указан только в тексте описания |
| `03_incomplete.json` | без названия: сервис отвечает 422 со списком недостающих полей и не обращается к LLM |

## Настройки (`.env`)

| Переменная | Назначение |
|---|---|
| `OPENROUTER_API_KEY` | ключ OpenRouter |
| `OPENROUTER_MODEL` | идентификатор модели |
| `OPENROUTER_BASE_URL` | адрес API, по умолчанию `https://openrouter.ai/api/v1` |
| `LLM_TEMPERATURE` | температура, по умолчанию `0.2` |
| `LLM_MAX_TOKENS` | лимит токенов ответа; на обычной модели хватает 4000 |
| `LLM_TIMEOUT_SECONDS` | таймаут запроса к модели |
| `LLM_MAX_RETRIES` | повторы при сетевых ошибках, 429 и 5xx |
| `LLM_JSON_MODE` | передавать `response_format=json_object`; отключите, если модель его не поддерживает |
| `GENERATION_MAX_ATTEMPTS` | сколько раз модель может исправить ответ, не прошедший проверку |
| `LOG_LEVEL` | уровень логов: `DEBUG`, `INFO`, `WARNING`, `ERROR` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_HOST`, `POSTGRES_PORT` | подключение к базе; в Docker хост подставляется автоматически |

## API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/cards` | сгенерировать карточку (тело — JSON товара) |
| `POST` | `/api/v1/cards/analyze` | проверить полноту данных без вызова LLM |
| `GET` | `/api/v1/cards` | история генераций (`limit`, `offset`) |
| `GET` | `/api/v1/cards/{id}` | карточка в JSON и Markdown |
| `GET` | `/api/v1/cards/{id}/markdown` | только Markdown, удобно копировать |
| `GET` | `/health` | проверка, что сервис жив |

Формат входного JSON:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

## Как устроена защита от выдуманных характеристик

Главное решение: **модель не формирует список характеристик.** Она пишет только тексты.

1. **Характеристики собирает код** (`KeySpecBuilder`) из `specs`. Рекомендуемые для КИП характеристики, которых нет во входе (справочник в `core/spec_catalog.py`), попадают в список со значением «данных нет».
2. **Характеристики из описания принимаются только с цитатой.** Модель может вернуть `extracted_specs` с дословной цитатой из `description`. Код проверяет, что цитата есть в тексте и числа значения входят в цитату. Неподтверждённые записи отбрасываются с предупреждением.
3. **Сверка чисел.** Все числа в заголовке, описании, запросах и коммерческом блоке сравниваются с числами из входных данных (`1,6` и `1.6` считаются одним числом).
4. **Цикл исправления.** Если ответ не прошёл проверку (длина, число запросов, лишние числа, битый JSON), модель получает список конкретных проблем и исправляет ответ. Проблемы, оставшиеся после всех попыток, не скрываются, а попадают в `warnings`. Слишком длинный заголовок обрезается по границе слова.
5. **Низкая температура** (`0.2`) и `response_format=json_object`.

## Промпты

Лежат в `app/prompts/product_card.py`.

- **System.** Роль: копирайтер B2B-магазина КИПиА. Первыми идут правила достоверности, они приоритетнее остальных требований: единственный источник фактов — блок `<product>`, числа и единицы не меняются, нельзя писать о цене, наличии и сертификатах, нельзя «обычно» и «как правило». Затем требования к каждому полю. Длина описания задана ещё и в словах (130–160), потому что символы модели считают плохо. В конце — точная JSON-схема ответа.
- **User.** Входные данные в теге `<product>`: только заполненные характеристики, пустые поля помечены «данных нет». Отдельный блок `<missing_specs>` перечисляет, чего не хватает.
- **Correction.** Список конкретных проблем от валидатора и просьба исправить только их.

## Обработка неполных и некорректных данных

- Синтаксически неверный JSON → `400` с позицией ошибки. Неверные типы полей → `422` со списком полей.
- Пустые строки и `null` считаются отсутствующими значениями, пробелы обрезаются.
- Без названия, а также без характеристик и описания одновременно генерация не запускается: `422` и `missing_fields`.
- Нет производителя или описания, пустая характеристика, отсутствует рекомендуемая характеристика → карточка генерируется, в ней есть раздел «Требует уточнения».
- Ошибки LLM (таймаут, 429, пустой ответ) сохраняются в БД со статусом `failed`, запросы к OpenRouter повторяются на временных ошибках.

## Частые проблемы

| Симптом | Причина и решение |
|---|---|
| `429 Provider returned error` | лимит провайдера модели, чаще всего у `:free`-моделей; смените модель или пополните баланс OpenRouter |
| `Модель вернула пустой ответ (finish_reason=length, рассуждения=есть)` | reasoning-модель потратила весь лимит токенов на рассуждения; возьмите обычную instruct-модель |
| `Модель вернула пустой ответ (finish_reason=stop)` | модель не поддерживает JSON-режим; поставьте `LLM_JSON_MODE=false` |
| `503 LLM не настроена` | не заполнены `OPENROUTER_API_KEY` или `OPENROUTER_MODEL` |
| текст не укладывается в длину | модель не справилась за все попытки; ответ вернётся с предупреждением, попробуйте модель покрупнее |

## Ограничения

- Справочник рекомендуемых характеристик один на все КИП. Для механического манометра пункты «питание» и «интерфейсы» будут отмечены «данных нет», хотя для него они неприменимы.
- Проверка достоверности сверяет только числа. Выдуманный нечисловой факт (например, материал, которого нет во входных данных) автоматически не ловится: от этого защищает промпт и ручная проверка менеджером.
- Длину текста контролирует цикл исправления, код сам текст не дорабатывает.
- Генерация синхронная, без очереди: запрос ждёт ответа модели.
- Нет авторизации и ограничения частоты запросов.

## Возможные улучшения

- Справочники характеристик по категориям приборов (манометры, датчики, расходомеры) с автоопределением категории.
- Второй проход LLM, который сверяет каждое утверждение текста со входными данными, в том числе нечисловые.
- Structured outputs (`json_schema`) для моделей, которые их поддерживают.
- Пакетная обработка CSV/XLSX и фоновые задачи со статусом генерации.
- Редактирование и согласование карточки в UI, экспорт в формат CMS.
- Набор эталонных товаров и автоматическая оценка качества при смене модели или промпта.
